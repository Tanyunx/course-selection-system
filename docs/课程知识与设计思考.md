## 二、关键决策的思考过程

### 2.1 先做 mock，再做数据库版 —— 顺序是刻意的

作业允许"开始时数据先用 mock，保存在本地 JSON"。这条不是妥协，而是**分阶段降风险**：

1. **阶段一（mock）**先把"业务规则对不对"这件事验证完——批次准入、时间冲突、
   单双周、学分上限、先修、候补递补、幂等、限速。业务引擎直接跑在浏览器里，
   数据内嵌为 JSON，刷新即重置。这一阶段完全不碰网络和数据库，
   因此规则类 bug 不会被环境问题掩盖。
2. **阶段二**把同一套规则搬到服务端。因为规则已经验证过了，此时出问题必然是
   "移植引入的"，排查范围一下子缩小到 SQL 方言、事务边界、序列化格式三件事上。

**实际效果**：阶段二移植过程中真的只出了这几类问题（文本块空白、占位符个数、
`FOR UPDATE` 限制、整数除法），没有一条是业务规则理解错了。这验证了分阶段的判断。

### 2.2 为什么是 Spring Boot，而不是 Servlet/JSP 或 SSM

Java Web 是一个领域，不是某个框架。演进路线大致是：

```
Servlet / JSP          手写 doGet/doPost、手拼 HTML、web.xml 配置
      ↓
SSM (Spring + SpringMVC + MyBatis)   分层清晰了，但要写一堆 XML 或注解配置
      ↓
Spring Boot            约定优于配置，内嵌 Tomcat，一个 main 方法就能起服务
```

这门课要求"前后端独立"，前端是原生 HTML/CSS/JS 单页应用。这种情况下：

- **JSP 不合适**：JSP 是服务端渲染模板，和"前端独立"直接冲突。
- **裸 Servlet 不合适**：要手写大量参数解析、JSON 序列化、异常处理样板代码，
  这些和课程要考的"架构与并发"无关，属于无谓的噪音。
- **SSM 偏重**：本项目没有复杂 ORM 需求，MyBatis 的价值（复杂动态 SQL 与映射）
  在这个规模下体现不出来，反而多一层需要理解的抽象。
- **Spring Boot 合适**：内嵌容器省掉外置 Tomcat 的部署复杂度；
  `@RestController` + Jackson 让"返回 JSON"变成默认行为；
  事务、连接池、定时任务都有开箱即用的标准做法。

**结论**：选 Spring Boot 不是为了"新"，而是因为它把与课程考点无关的管道代码压到了最少，
让代码主体集中在业务规则和并发控制上。

### 2.3 为什么用 JdbcTemplate 而不是 MyBatis / JPA

这是本项目最值得说明的一个取舍。选课系统的难点不是"表多"，而是**有几条 SQL 必须逐字可控**：

```sql
UPDATE t_course_offering
   SET enrolled = enrolled + 1
 WHERE id = ? AND enrolled < capacity AND status <> 0
```

这条语句是防超卖的全部秘密：把"判断还有没有名额"和"名额加一"压进**同一条 SQL**，
由数据库的行锁保证这两件事之间不可能插进别的请求。它能不能生效，
取决于它是否被原样送到数据库。

- **JPA/Hibernate**：为了拿到行锁语义，得用 `@Version` 乐观锁或 `@Lock`，
  生成的 SQL 还要靠日志确认；"条件更新"这种写法反而要绕。
  而且 ORM 的持久化上下文会给并发调试引入额外的心理负担（一级缓存、脏检查时机）。
- **MyBatis**：SQL 是手写的，能满足要求，但要维护 XML/注解映射，
  对本项目 18 张表的规模来说收益有限。
- **JdbcTemplate**：SQL 原样可见，返回行数直接用；代价是要手写 `Map` → 对象的取值，
  这部分由 `db/Db.java` 的 `num/decimal/str/flag` 助手统一吸收。

**结论**：评审时打开 `EnrollmentService.java` 就能看到防超卖那一条 SQL **本身**，
而不需要先理解一层 ORM 的行为。对"证明我在数据库层面做了并发控制"这个目标来说，
这种"把关键语句摆在明面上"的价值超过抽象的优雅。

### 2.4 防超卖的三种方案对比与选择

| 方案 | 做法 | 问题 |
| --- | --- | --- |
| A. 应用层锁 | `synchronized` 或 `ReentrantLock` 包住"查余量 → 判断 → 写库" | **多实例部署直接失效**；单实例下也把选课串行化了，性能与可扩展性都差 |
| B. Redis 预扣 | 余量放 Redis，`DECR` 成功才写库 | 引入外部依赖与"缓存与数据库不一致"问题；需要补偿逻辑；对课程作业属于过度设计 |
| C. **数据库条件更新**（本项目） | `UPDATE ... SET enrolled = enrolled + 1 WHERE id = ? AND enrolled < capacity`，看受影响行数 | 无外部依赖；**多实例天然安全**；正确性由数据库保证 |

选 C 的理由：

1. **正确性最强**：并发控制交给了数据库，而数据库的并发控制是被证明过的。
   应用层再怎么出 bug（多线程、多实例、GC 停顿），都不可能突破这一层。
2. **没有额外依赖**：不引入 Redis，服务器 2 核 2G 也能跑，运维成本低。
3. **性能足够**：行锁只在"同一门课"上竞争，不同课程之间互不影响；
   同一门课的抢课本身就是天然的串行场景，锁等待时间极短。
4. **可验证**：受影响行数是 0 就代表"已满"，这个判断在代码里一眼可见，
   测试里也能用 8 并发直接打出来（见第五部分）。

同时**用唯一约束做最后防线**：`t_enrollment` 上建 `uk_student_offering (student_id, offering_id)`。
即使应用层逻辑写错、被重复调用，数据库也会拒绝第二条记录。
这是"纵深防御"的思路——应用层负责给出友好错误码，数据库负责保证不出错。

### 2.5 三层架构与"真正的前后端分离"

作业要求"前后端独立开"。很多实现把它做成"同一个进程里既托管静态页又提供接口"，
这在**代码分层**上是分开的，但在**部署**上还是同一个服务，不算严格的独立。

本项目的做法：

- 前端：`frontend/`，纯静态资源，**不含任何构建步骤**，Nginx 直接托管。
- 后端：`backend/`，独立可执行的 jar，只提供 `/api/**`，**只监听 `127.0.0.1:3000`**。
- 两者通过 Nginx 组合在同一个域名下：

```nginx
location /       { root .../frontend; try_files $uri $uri/ /index.html; }
location /api/   { proxy_pass http://127.0.0.1:3000; }
```

好处：

1. 前端可以单独替换（换 CDN、换框架）而不动后端。
2. 后端不暴露公网端口，攻击面小。
3. **浏览器只看到同源**，跨域问题在这个结构下天然不存在。

**关于"跨域"和"安全证书"**：开发阶段前端跑在 `5500`、后端跑在 `3000`，
确实跨域，所以后端实现了 `CORS_ORIGINS` 白名单（`WebConfig.java`），
并且用 `Authorization: Bearer` 令牌而不是 Cookie，因此可以 `allowCredentials=false`，
避免"凭据 + 通配符来源"这个不安全组合。
上线后前后端同源，CORS 收敛为具体域名，HTTPS 由 certbot 覆盖，
于是"跨域"和"证书"两件事都从根上解决了。

## 三、用到的课程知识对应表

### 3.1 数据库原理

| 知识点 | 具体应用 | 位置 |
| --- | --- | --- |
| **ACID 与事务** | 选课的"占名额 → 校验 → 落库"、换课的"先占后放"整体原子；失败全部回滚，已占名额自动归还 | `Db.withTransaction`、`EnrollmentService` |
| **隔离级别与行锁** | 依赖 PostgreSQL 默认的 Read Committed + 行级写锁：`UPDATE ... WHERE enrolled < capacity` 在行上串行 | `occupySeat` |
| **悲观锁 `SELECT ... FOR UPDATE`** | 候补排位号分配前先锁开课行；退课流程锁选课记录行 | `WaitlistService.join`、`EnrollmentService.drop` |
| **唯一约束作为并发防线** | `uk_student_offering` 保证同一学生同一开课只有一条有效记录 | `schema-pg.sql` |
| **条件更新 / 乐观并发控制** | 用"受影响行数是否为 0"判断竞争结果，而不是先查再判断 | `occupySeat` |
| **UPSERT** | 候补记录用 `INSERT ... ON CONFLICT (student_id, offering_id) DO UPDATE` 一条语句完成"新建或复活" | `WaitlistService.join` |
| **索引设计** | 为高频查询建索引：`idx_offering_term`、`idx_enroll_student`、`idx_waitlist_status` 等 | `schema-pg.sql` |
| **触发器** | PostgreSQL 没有 MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`，用 `BEFORE UPDATE` 触发器统一维护 `updated_at` | `set_updated_at()` + 18 个触发器 |
| **约束与数据完整性** | 18 张表全部声明主键、外键、唯一约束、非空与默认值；用枚举型 `SMALLINT` + `COMMENT` 表达数据字典 | `schema-pg.sql` |
| **范式与反范式** | 主体按第三范式设计；`t_course_offering.enrolled` 是刻意的**反范式冗余**（可由 `t_enrollment` 统计得到），目的是让"判断+计数"能在一条 SQL 里完成原子更新 | `schema-pg.sql` |
| **序列与自增** | 从 MySQL 迁到 PostgreSQL 后需用 `setval(pg_get_serial_sequence(...))` 校正 identity 序列，否则新插入会撞主键 | `tools/mysql2pg.py` |

> 关于 `enrolled` 的反范式冗余值得多说一句：如果每次都 `SELECT COUNT(*) FROM t_enrollment` 来判断余量，
> 那么"统计"与"插入"之间就有时间窗口，两个请求可能都读到"还有 1 个名额"。
> 把它物化成一个可以原子自增的列，才能让条件更新成立。这就是"为了并发正确性而做的反范式"。

### 3.3 计算机网络

| 知识点 | 具体应用 |
| --- | --- |
| **HTTP 请求/响应模型** | 全部接口基于 HTTP + JSON；`GET/POST/PUT/DELETE` 语义与资源对应 |
| **状态码与业务码的双层设计** | HTTP 层统一 200（业务错误也用 200），业务层用 `code` 区分；只有真正的路由不存在才用 404 |
| **反向代理** | Nginx 把 `/api` 反代到后端，`proxy_set_header X-Real-IP / X-Forwarded-For / X-Forwarded-Proto` 传递真实客户端信息 |

| **HTTPS / TLS 证书** | Let's Encrypt 签发，certbot 自动改写 Nginx 配置并注册续期任务；80 → 443 强制跳转 |
| **静态资源与缓存** | Nginx 对 CSS/JS/图片设置 `expires`，gzip 压缩文本类资源 |
| **令牌鉴权（无状态 vs 有状态）** | 采用"自包含 HMAC-SHA256 令牌 + 服务端会话表"的混合方案：令牌携带身份避免每次查库，会话表支持主动注销与空闲超时 |

> 令牌为什么不用 JWT 库而自己实现：本项目需要的不只是"签名正确"，还要
> "服务端可主动失效"。自包含载荷结构（`userId/username/realName/role/iat/exp/jti`）
> 完全对齐原实现，签名比较用 `MessageDigest.isEqual` 做**定长比较**以抗时序侧信道，
> 代码不到 200 行，可读性优于引入一个库。

### 3.5 程序设计语言与并发编程

| 知识点 | 具体应用 |
| --- | --- |
| **面向对象与封装** | `Db` 把 JDBC 细节封在内部，业务层只看到 `query/update/withTransaction` 这类语义化方法 |

### 3.6 信息安全

| 知识点 | 具体应用 |
| --- | --- |
| **口令存储** | BCrypt 加盐哈希；种子脚本里是 `__PWD_HASH__` 占位符，导入时替换——**版本库里连哈希都没有** |
| **身份认证** | 登录签发 HMAC 令牌；连续失败 5 次后要求图形验证码 |
| **访问控制** | RBAC 四角色 + 接口级 `@RequireRole`；越权访问写审计日志（留下追溯线索） |
| **最小权限** | 数据库用专用账号 `course_app` 只拥有本库权限，不用 `postgres` 超级用户跑应用 |
| **敏感信息不外泄** | 源码/脚本/SQL/systemd 单元全部不含口令；配置模板 `.env.example` 只留空值 |
| **防脚本刷课** | 60 秒窗口内写操作超过软阈值返回 9001，超过硬阈值要求安全验证 |
| **审计与追溯** | `t_audit_log` 记录登录、选课、退课、容量调整、越权访问等关键动作 |

> 顺带说明 token 的失效策略：会话保存在服务端 `SessionStore`，因此
> "注销"能立即生效（对比纯 JWT 只能等过期）；空闲 30 分钟自动失效。
> 代价是单机内存态，多实例部署时需要换成 Redis 或数据库——这一点在 README 的
> "未实现项"里明确标注了，属于已知边界而非疏漏。

## 四、核心流程的并发控制详解

以"学生选课"为例，走一遍完整的时序，说明每一步为什么这么排。

### 4.1 校验顺序

```
① 鉴权（令牌 + 角色）              → 1002 / 1003
② 幂等（requestId 命中直接返回）    → 返回首次结果
③ 批次时间窗口                     → 2005
④ 是否已选 / 是否已在候补           → 2006 / 2007
⑤ 占名额（条件更新，原子）          → 2001 已满
⑥ 时间冲突检测                     → 2002
⑦ 学分上下限                       → 2003
⑧ 先修课程                         → 2004
⑨ 落库 + 通知 + 审计
```

**为什么把"占名额"放在校验的前面（第 5 步），而不是最后？**

因为如果不先占名额，就存在这样的窗口：先查余量（有 1 个）→ 做冲突/学分/先修校验
（耗时较长）→ 再写库。两个并发请求都会通过"余量检查"，最终超卖。

反过来，"先占名额"把竞争压缩到了一个瞬间：只有拿到行锁并成功自增的那个请求继续往下走，
其余请求立刻得到 2001。代价是第 6~8 步失败时需要**回滚事务**把名额还回去——
这正是把整个流程包在一个事务里的原因：

```java
return db.withTransaction(() -> {
    long affected = db.update(
        "UPDATE t_course_offering SET enrolled = enrolled + 1 "
      + "WHERE id = ? AND enrolled < capacity AND status <> 0", offeringId);
    if (affected == 0) throw new BizException(ErrorCode.CAPACITY_FULL);   // 2001
    rules.assertNoConflict(...);   // 2002
    rules.assertCreditOk(...);     // 2003
    rules.assertPrereqOk(...);     // 2004
    return upsertEnrollment(...);  // 落库
});
```

`affected == 0` 就代表"没抢到"，抛异常后 `TransactionTemplate` 整体回滚，
名额、记录、通知全部回到调用前状态——**不会出现"占了名额但没选上"的脏数据**。

### 4.2 换课为什么是"先占后放"

换课 = 退掉 A + 选上 B，但它不能真的"先退再选"：如果先释放 A 的名额，
而 B 已经满了，学生就落得"两头空"。

所以顺序是：

```
① 锁住原选课记录（FOR UPDATE）
② 预占目标 B 的名额（条件更新，失败即 2009）  ← 先占
③ 冲突/学分/先修校验（冲突检测时排除"即将释放的 A"）
④ 释放 A 的名额
⑤ 重建选课记录（B）
```

第 ③ 步有个容易漏的细节：校验冲突时必须把 A 自己排除掉，否则"换到同一时间段的另一门课"
会因为"和已选的 A 冲突"而被拒绝。整个流程在一个事务里，
**任何一步失败都返回 2009 且原选课完全不变**。

### 4.3 候补递补为什么需要锁

名额释放时（学生退课、教务扩容），要按排位通知第一个候补。
如果两个人同时退同一门课，就可能出现"同一门课释放了 2 个名额，
但两次递补都取到了队首那一个人"，导致第二个人被漏掉。

处理方式：

```
① 锁住开课行（SELECT id FROM t_course_offering WHERE id = ? FOR UPDATE）
② 取 queue_no 最小的候补者
③ 重新执行完整校验（批次/冲突/学分/先修都重跑一遍 —— 排队期间条件可能已变）
④ 通过 → 占名额 + 生成"候补递补"来源的记录 + 置为已递补 + 设 24 小时确认期
   不通过 → 置为已失效 + 发"递补失败"通知 + 顺延下一名（最多循环 20 次）
```

③ 这一步是设计文档里特别强调的：**候补排队期间学生的课表可能已经变了**，
所以递补时必须重新校验。验收用例 TC-11 专门验证这个场景：
候补者在此期间被安排了同时间段的另一门课 → 递补失败、自动顺延。

### 4.4 "多人同时抢同一门课"的四层防线

作业要求里的"数据冲突要在数据库控制，事务，要考虑多人"，落到实现上就是这条链路。
按"越靠下越可靠"的顺序排：

| 层 | 手段 | 位置 | 挡住什么 |
| --- | --- | --- | --- |
| ① 应用幂等 | 同一 requestId 命中缓存直接返回首次结果 | `Guard.idempotent` | 同一学生重复点击、网络重发、浏览器后退重提 |
| ② 应用限速 | 窗口内超过软阈值返回 9001，超过硬阈值要求完成安全验证 | `Guard.rateLimited` + `RateLimitStore` | 脚本刷课、恶意抢占 |
| ③ 事务 + 行锁 | 条件更新原子占名额，失败即 2001；后续校验失败整体回滚 | `EnrollmentService.enroll` + `Db.withTransaction` | 超卖、脏数据、名额占住不放 |
| ④ 数据库约束 | `uk_student_offering (student_id, offering_id)` 唯一键；`ck_offering_enrolled CHECK (enrolled >= 0)` | `schema-pg.sql` | 应用层逻辑写错时的最后兜底 |

四层是**纵深防御**关系，不是四选一：应用层负责给出友好错误码，数据库负责保证"无论如何都不会错"。

#### 一条"条件更新"为什么足够——READ COMMITTED 下的串行化

PostgreSQL 默认隔离级别是 **READ COMMITTED**（本项目没有改过隔离级别）。两个学生同时点同一门课时：

```sql
UPDATE t_course_offering
   SET enrolled = enrolled + 1
 WHERE id = 7 AND enrolled < capacity AND status <> 0;
```

- 先到的 T1 拿到该行的**行级排他锁**，自增成功并提交；
- 后到的 T2 在申请同一行的锁时**阻塞等待**（不是立刻失败，也不是读到旧值）；
- T1 提交后 T2 取得锁，数据库会**基于最新的行版本重新判断 WHERE 条件**，此时
  `enrolled` 已等于 `capacity`，条件不成立 → 受影响行数 0 → 返回 2001。

**关键点**：`判断余量` 与 `占用名额` 在**同一条 SQL** 里完成，中间不存在任何时间窗口能让两个事务都通过判断。

这正是**不写成"先 SELECT 查余量、再 UPDATE 自增"**的原因——那种写法无论中间隔多短，
都存在"两个请求都读到余量 1"的竞态窗口，也就是经典的超卖。

#### 事务边界为什么必须包住后面所有校验

"先占名额再校验"把并发竞争压缩到一个瞬间，代价是后面任何一步失败都必须把名额还回去。
所以整个流程包在 `Db.withTransaction` 里：

```
占名额 → 时间冲突 → 学分 → 先修 → 落库
   任一步抛异常
      ↓
TransactionTemplate 回滚
      ↓
enrolled 自增被撤销、选课记录不落、通知不发
学生看到 2002 / 2003 / 2004，课程余量与操作前完全一致
```

**不会出现"占了名额但没选上"的脏数据**——这是 `tests/concurrency.js` 场景① 要专门断言
"选课记录条数 == enrolled" 的原因：冗余计数列最容易和明细表对不上。

#### 同一个学生的重复提交：四层防线**不够**，得补第五层

注意区分两种"并发"：

- **不同学生抢同一个名额** → 靠 ③ 行锁串行化（上面讲的）；
- **同一个学生重复提交同一门课** → 原本以为靠 ① 幂等 + ④ 唯一键就够了。

**但压测证明这个想法是错的。** ① 幂等是按 `requestId` 去重的，
如果学生（或脚本）在极短时间内用**不同** `requestId` 并发提交同一门课，
幂等缓存会**全部落空**：

```
时刻 T：N 个请求同时到达，N 个事务同时执行

  T1: 查重 → "还没选" ✓ ┐
  T2: 查重 → "还没选" ✓ ├─ 都读到同一个旧快照
  T3: 查重 → "还没选" ✓ ┘

  T1: enrolled + 1  ← 成功
  T2: enrolled + 1  ← 成功   ← 名额被加了 N 次！
  T3: enrolled + 1  ← 成功

  T1: INSERT t_enrollment ← 成功
  T2: INSERT t_enrollment ← 唯一键冲突，回滚
  T3: INSERT t_enrollment ← 唯一键冲突，回滚
```

结果：**`t_enrollment` 只有 1 条（④ 确实兜住了），但 `enrolled` 被加了 3 次**——
T2、T3 回滚时撤销的是**它们自己那次自增**，而它们自增的是同一个已经"成功过一次"的计数。

实测数据：同一门课 10 连发后 `enrolled=5`、真实记录只有 1 条，
**凭空少掉 4 个名额**，把后来想选这门课的同学全挡在门外。

> 这是冗余列最阴险的失真形态：**明细表是对的，计数列是错的，而且错得"看不出来"**——
> 页面显示"已满"，但你去数据库数记录数只有 1 条。`concurrency.js` 场景② 用**同一个** requestId
> 连发，所以幂等缓存挡住了，从没暴露这个问题。

**第五层：事务级咨询锁（本次补上）**

```sql
SELECT pg_advisory_xact_lock(?)   -- 键 = student_id * 1_000_000 + offering_id
```

持锁之后再查一次重复，后到的请求直接以 2006 失败，**根本没机会去占名额**。
为什么选咨询锁而不是应用内 `synchronized`：

| 方案 | 跨线程 | 跨连接池 | 跨多实例 | 忘记解锁的风险 |
| --- | --- | --- | --- | --- |
| `synchronized` / `ReentrantLock` | ✓ | ✓ | ✗ 多实例各锁各的，等于没锁 | 中 |
| 咨询锁 `pg_advisory_xact_lock` | ✓ | ✓ | ✓ 锁在数据库里 | 无（随事务自动释放） |

键的设计要保证"同一个 (学生, 开课) 二元组必然映射到同一个键，不同二元组尽量不碰撞"：
`student_id * 1_000_000 + offering_id` 在本题量级下足够（学生 id 与开课 id 都远小于 100 万）。
选它而不选"锁整张表"，是为了让**不同学生选不同课完全互不影响**，不牺牲吞吐。

**这一层也同时保护了换课**：两人同时换到同一门只剩 1 个名额的课，
如果不加锁，两人都会 `occupySeat` 成功、再在唯一约束上撞车回滚，
名额同样会被白扣——压测场景 5 就是专门验证这个的。

### 4.5 "同一个学生同时段选两门课"怎么检测

这里"同一时间"是另一种含义：不是"很多人同时点"，而是**两门课的上课时间重叠**。
判定集中在 `RuleService.detectConflict`，用一条表自连接 SQL 完成：

```sql
FROM t_course_schedule s1
JOIN t_course_schedule s2
  ON s2.weekday = s1.weekday                                   -- 同一星期几
 AND s1.start_period <= s2.end_period                          -- 节次区间相交
 AND s2.start_period <= s1.end_period                          --   （区间重叠的标准判定）
 AND NOT ((s1.parity = 1 AND s2.parity = 2)                   -- 单双周不互斥
       OR (s1.parity = 2 AND s2.parity = 1))
JOIN t_enrollment e  ON e.offering_id = s2.offering_id AND e.student_id = ? AND e.status = 1
JOIN t_course_offering o2 ON o2.id = s2.offering_id AND o2.term_id = ?
```

**三个容易漏的细节，代码里都处理了：**

1. **一门课有多个时段时，任一时段冲突即整体冲突。** 所以是从 `t_course_schedule` 自连接、
   取 `DISTINCT`，而不是"只比第一个时段"。
2. **换课时必须排除"即将释放的原课程"。** `detectConflict(offeringId, studentId, termId, exclude...)`
   的可变参数就是干这个的——否则"换到同一时段的另一门课"会被自己原来的课挡住，
   学生永远换不过去。调用点在换课分支：`rules.detectConflict(toOfferingId, studentId, termId, fromOfferingId)`。
3. **相邻节次跨校区只提醒、不拦截。** 第二段 SQL 查"同一天 + 节次紧邻（`end_period + 1`）+ 校区不同"，
   结果作为 `tightTransfers` 在选课成功后随响应返回，前端提示"赶课提醒"，**不阻断选课**。
   规则是可配置的边界，不是硬约束——这是把教学管理经验（跨校区赶课时间不够）做成"提醒"而不是"否决"。

**与 4.4 的关系**：4.4 保证"名额不会超卖"，4.5 保证"课表不会自我冲突"。
两者都在同一个事务里，且**顺序不能换**——先占名额（可能失败 2001），
冲突检测排在后面（可能失败 2002），失败都靠回滚收尾。

## 五、并发正确性的实测验证

"在数据库控制冲突"这句话需要一个可复现的证据。`tests/concurrency.js` 就是这份证据。

### 场景 ① 8 人同时抢 3 个名额

做法：教务建一门容量为 3 的新课（无排课，因此不会产生时间冲突），
8 名学生用 `Promise.all` **同时**发出选课请求。

一次真实运行的输出：

```
场景 1：8 人并发抢 3 个名额
  通过  成功人数恰好等于容量 3  → 成功 3 人（codes=0,2001,2001,2001,2001,2001,0,0）
  通过  其余请求被容量拦截为 2001  → 2001 共 5 条
  通过  没有其他异常错误码  → 无
  通过  数据库 enrolled 严格等于 3（未超卖）  → enrolled=3 capacity=3
  通过  remaining 不为负  → remaining=0
  通过  选课记录条数与 enrolled 一致  → 记录 3 条 / enrolled=3
```

为什么这组断言能证明问题：

- `codes` 是**逐请求**的结果，8 个请求里恰好 3 个 `0`（成功）、5 个 `2001`（已满），
  说明竞争确实发生了，而不是靠串行化"看起来正确"。
- `enrolled` 是**直接查数据库**得到的，不是接口返回的，所以能排除"接口说成功但没写库"的情况。
  它严格等于 3，证明没有超卖。
- `remaining >= 0` 排除了"负数余量"这种典型的计数错误。
- **选课记录条数 = enrolled**：这一条是在防"名额加了但记录没插"或反之的**双写不一致**——
  反范式冗余列最容易出的问题就是它和明细表对不上。

### 场景 ② 同一 requestId 重复提交

做法：同一学生用同一个 `requestId` 连发两次选课。

断言：第二次返回的 `code` 与 `message` 与第一次**完全一致**、`enrolled` 仍为 1、
选课记录仍为 1 条。这验证了幂等缓存确实拦住了第二次请求，而不是"第二次靠唯一约束报错"——
两者的用户体感完全不同（前者与首次结果一致，后者会看到错误提示）。

### 场景 ③ 退课后名额自动递补给候补第一位

做法：A 占满唯一名额 → B 加入候补（排位 1）→ A 退课。

断言：退课返回中带 `PROMOTED` 递补动作、`enrolled` 仍为 1（名额被 B 接手，而不是凭空少一个）、
B 的候补状态变为"已递补"、B 的已选列表中出现该课程。这验证了"释放 → 递补"这条链路的完整性与原子性。

### 场景 ④ 高压压测（`tests/stress.js`，23 项）

上面三套是**黑盒 HTTP 级别、每个场景只跑一次**。它能证明"基本不超卖"，
但证明不了"多人选课冲突被彻底解决"——真实抢课是持续高压、反复争夺的。

所以补了一套压测，把四类不变量放到远超常规的强度下反复捶打：

| 代号 | 不变量 |
| --- | --- |
| A | 不超卖：`enrolled` 恰好等于 `capacity`，不为负 |
| B | 不重复：同一学生并发重复提交只产生一条有效记录 |
| C | 不丢名额：并发退课 + 候补递补后名额守恒 |
| D | 不脏数据：冗余列 `enrolled` 与真实有效记录数**始终**一致 |

五个场景与设计取舍：

| 场景 | 做法 | 验证 | 设计要点 |
| --- | --- | --- | --- |
| 1 | 8 人 × 3 轮反复抢容量 3 的课 | A/B/D | 跨轮换新 requestId，模拟"反复抢"而非"重复提交" |
| 2 | 同一学生同一 requestId 并发 10 次 | B | 验证幂等缓存真的挡住并发（不只是串行重发） |
| 3 | 同一学生**不同** requestId 并发 6 次 | B/D | **绕过幂等**，直击唯一约束与咨询锁 |
| 4 | 容量 2、2 人在读 + 3 人候补，并发退课 | C | 验证递补顺序（从前到后）与名额守恒 |
| 5 | 两人并发换课到只剩 1 个名额的课 | A/C | 只能一人成功，**失败方必须保留原课**（先占后放不能丢名额） |

**限速怎么处理**：后端限速按**用户**隔离（软 10 / 硬 20，60 秒窗口）。
所以并发强度靠**增加参与人数**提升，而不是让单用户狂刷；
对必须"同一学生连续写"的场景，脚本开始时**等待一个限速窗口**（62 秒）。
等待是确定性的——限速本身就是要验证的行为，跳过只会得到假红。

**为什么必须独占干净库**：脚本会插"压力测试校区"的测试开课；
低学分课程只有 5 门、教师 4 位，共 20 个「课程 × 教师」组合，
而脚本要建 7 门测试课。在脏库上重复跑会把这 20 个组合占满，
脚本会**明确报错提示先重建**，而不是静默跑出假绿。

#### 压测抓出的两个真实缺陷

这套压测**第一次运行就抓出了两个缺陷**，其中一个此前任何测试都没覆盖到：

**① 并发重复提交导致名额泄漏**（详见 §4.4 第五层）
同一学生用不同 requestId 并发提交同一门课，10 连发后 `enrolled=5`、真实记录仅 1 条，
**凭空少掉 4 个名额**。根因是幂等缓存按 requestId 去重，并发时全部落空，
N 个事务同时"查重 → 占名额"，只有一条记录落库、其余回滚，但名额已被加多次。
修复：事务内加 `pg_advisory_xact_lock` 咨询锁，键 = `(student_id, offering_id)`。

**② 换课接口抛 500（`9002`）**
`RuleService.detectConflict` 的 SQL 写的是 `NOT IN (?,?)`（占位符显式展开），
但传参时把整个 `exclude` 列表当成**一个**参数传了进去。
普通选课路径 `exclude` 只有 1 个元素，占位符数刚好对上，**侥幸不报错**；
只有换课（`exclude` 有 2 个元素）才触发，因此长期潜伏。
修复：把 `exclude` 逐个摊平成独立参数。

> 这两个缺陷的共同点：**都不在"读代码就能发现"的显眼位置**——
> 前者是并发时序问题，后者只在特定调用路径上成立。
> 这也正是"多人选课冲突必须用压测证明"的理由：阅读实现只能确认"看起来对"。

## 六、从 MySQL 迁移到 PostgreSQL 的思考与踩坑

### 6.1 迁移策略

作业要求用 PostgreSQL，但第一版是按 MySQL 写的，而 MySQL 的建表脚本、种子数据、
验收测试都已经验证过了。**重写一遍不如"只改方言、不改语义"**，于是：

1. 写一个转换器 `tools/mysql2pg.py`，把 MySQL 种子脚本转成 PostgreSQL 脚本，
   把每条改写规则写进脚本注释——**规则是可见、可复查的**，而不是"手工改了一遍"。
2. 保留 18 张表的表名、列名、约束名不变（`t_` 前缀、`uk_`/`idx_`/`fk_` 前缀），
   这样原验收测试的 SQL 大部分可以继续用。
3. 把 JDBC 层面的差异收在 `db/Db.java` 一个文件里，业务代码不感知。

### 6.2 实际踩到的坑（都有具体修复）

**坑 1：整数除法截断。**
MySQL 的 `/` 返回小数，`o.enrolled / o.capacity` 可以直接用来算利用率；
PostgreSQL 的整数相除结果还是整数，利用率会恒为 0 或 1。
→ 改成 `o.enrolled::numeric / NULLIF(o.capacity, 0)`，并把 `ROUND` 的参数显式转 `numeric`。
`NULLIF` 是为了容量为 0 时不产生除零错误。

**坑 2：`IN (?)` 不会自动展开。**
MySQL 驱动会把数组参数展开成 `IN (1,2,3)`；PostgreSQL JDBC 会报参数类型错误。
→ 在 `Db.prepare()` 里按参数类型自动展开成 `IN (?,?,…)`；
集合为空时展开为 `IN (NULL)`（语义上"永不匹配"，避免生成非法 SQL）。

**坑 3：没有 `insertId`。**
MySQL 的 `result.insertId` 返回自增主键；PostgreSQL 要用 `INSERT ... RETURNING id`。
→ `Db.insertReturningId()` 自动补 `RETURNING id` 并取回。

**坑 4：`FOR UPDATE` 不能和聚合函数一起用。**
这一条最隐蔽。`SELECT COALESCE(MAX(queue_no), 0) FROM t_waitlist WHERE offering_id = ? FOR UPDATE`
在 MySQL 下能跑，在 PostgreSQL 下直接报 `0A000 feature_not_supported`。
更麻烦的是：HikariCP 检测到这种错误会把连接标记为 broken，
紧接着事务回滚也失败，于是前端只看到一个笼统的 `9002 系统繁忙`，
日志里最外层是 `JDBC rollback failed`，**真正的 SQL 错误被埋在里面**。
→ 改成先 `SELECT id FROM t_course_offering WHERE id = ? FOR UPDATE` 锁住开课行，
把同一门课的入队串行化，再取 `MAX(queue_no)`。语义等价，且是 PG 允许的写法。

**坑 5：`public` schema 的属主变了。**
PostgreSQL 15 起 `public` schema 归 `pg_database_owner`，
只建库不显式改属主的话，应用账号导入建表脚本会 `permission denied for schema public`。
→ 建库脚本增加 `ALTER DATABASE ... OWNER TO` 与 `ALTER SCHEMA public OWNER TO`。

### 6.3 语言层面的坑：Java 文本块会吃掉行尾空白

Java 的文本块（`"""`）会**剥离每行行尾的空白**。于是这段看起来没问题的代码：

```java
db.query("""
        SELECT ... FROM t_course_offering o
         WHERE """ + where + " ORDER BY ...", params);
```

会被拼成 `... WHEREo.term_id = ? ...`，数据库报 `syntax error at or near "WHEREo"`。
→ 用 `\s` 转义（Java 15+ 支持，是文本块里唯一不会被剥离的空白写法）写成 `WHERE\s"""`。
同样的写法一共有 3 处，属于同源缺陷。

**这个坑还引出一个更值得记的教训**：为了在代码里注释说明这件事，
我在 SQL 字符串的注释里写了一个带 `?` 的示例，
结果 `Db.prepare()` 把注释里的 `?` 也当成了占位符。
当时它的实现遇到"占位符多于参数"只是**默默补一个 `null`**，
于是错误最终由 PostgreSQL 抛出来：`栏位索引超过许可范围：4，栏位数：3`，
排查成本非常高。

修复分两层：

1. 注释里不再出现裸的 `?`（根治）。
2. `Db.prepare()` 在"占位符多于参数"时**立刻抛异常并打印完整 SQL**（治本）。

第 2 条是这次调试带来的最重要的一条工程习惯：**当一个工具的容错行为会掩盖调用方的错误时，
应该让它失败得更响，而不是更安静。**

## 七、测试策略

### 7.1 三层验证，各管一段

| 层次 | 手段 | 管什么 | 位置 |
| --- | --- | --- | --- |
| 规则正确性 | Node 直接驱动内嵌引擎，74 项断言 | 业务规则本身对不对（不受网络/数据库干扰） | `tools/test-engine.js` |
| 接口契约 | HTTP 黑盒冒烟，19 项 | 路由、鉴权、返回体结构、分页、错误码 | `tests/smoke.js` |
| 端到端场景 | HTTP 黑盒验收，15 项 | 完整业务流程与边界（并发、幂等、冲突、递补、越权、限速） | `tests/acceptance.js` |
| 并发一致性 | HTTP 并发 + 数据库校验，17 项 | 多人同时操作时数据是否仍然自洽 | `tests/concurrency.js` |

### 7.2 为什么坚持"黑盒"

所有测试**只通过 HTTP 调接口**发起业务动作；
数据库只被用于**读取校验**结果，绝不用来"直接造数据绕过业务逻辑"。
原因：

- 如果测试直接往数据库里插记录来准备场景，它会**假定**业务逻辑是对的，
  而不是**验证**业务逻辑是对的，测试就失去了意义。
- 唯一例外是验收测试里的测试夹具（`ZZTEST` 前缀的临时课程/开课），
  用来构造"满员课程""已冲突课程"这类难以通过接口高效构造的初始状态，
  且在 `teardown` 中自动清理。

### 7.3 测试自身也会出错

值得一提：`tests/concurrency.js` 在移植到 PostgreSQL 后连续失败了三次，
三次都不是被测系统的 bug，而是**测试自身**的问题：

1. 建课时只按"课程"维度挑候选，撞上种子数据里"同一门课已由该教师开设"的唯一约束。
   → 改成遍历"课程 × 教师"，挑第一个当前不冲突的组合。
2. 用 `x.offeringId` 读教务端开课列表，而该接口返回的是数据库列名 `offering_id`。
   → 与前端 `admin.js` 的取值方式对齐。

这条经验是：**测试用例的失败首先要怀疑测试自己**，尤其是它依赖了"当前数据的形状"时。
把这类假设显式化（比如把"已有组合"收集成 `existingPairs` 再排除），
测试才能在数据变化后依然稳定。

## 八、不足与改进方向

诚实地列出当前的边界，这些在 README「未实现项」里也有对应：

| 边界 | 现状 | 若要改进 |
| --- | --- | --- |
| 会话存储 | 服务端内存（`SessionStore`），进程重启需重新登录 | 换成 Redis 或数据库表；多实例部署的前提 |
| 无缓存层 | 余量直接查数据库 | 高并发抢课时可加 Redis 预扣 + 异步落库，但会引入一致性补偿逻辑 |
| 同步落库 | 选课在请求线程内完成 | 极端峰值下可用消息队列削峰；当前 2 核 2G 单机足够 |
| 无排队机制 | 超容量直接返回 2001 | 可选"排队中"状态与轮询，体验更平滑 |
| 候补递补的实时性 | 递补在退课事务内同步触发，另有 1 分钟定时回收超时未确认的递补 | 若候选很多，可改为异步事件驱动 |
| 换课可能死锁 | 两人同时互换（A→B 与 B→A）时双方都先锁自己的原选课记录，理论上有死锁可能；PG 会检测并终止一方（`40P01`），但**当前没有自动重试**，学生需手动重试一次 | 捕获 `40P01` 自动重试一次；或统一按 `offering_id` 升序加锁，破坏循环等待条件 |
| 未做真实压测 | 并发测试是 8 并发 × 3 容量的小规模场景 | 可用 JMeter/k6 做 1000 并发压测，观察 P95 与锁等待 |
| 未对接外部系统 | 学籍/成绩用本地表维护 | 按设计文档 1.3 的系统边界，属于明确的范围外 |

## 九、小结

用一句话概括这次作业的技术判断：

> **把并发正确性的责任交给最擅长这件事的那一层——数据库；
> 把与考点无关的复杂度从代码里移走——用 Spring Boot 和 JdbcTemplate；
> 把每个关键决策都变成可复现的验证——51 项断言。**

三个"阶段"的推进方式也值得记下来：先用 mock 验证规则 → 再用数据库验证并发 →
最后用 Linux + 域名 + HTTPS 验证部署。每一步只引入一类新的不确定性，
所以出问题时总是能定位到原因。这次移植 PostgreSQL 过程中出现的
整数除法、`IN` 展开、`FOR UPDATE`、文本块空白四类问题，
全部都是"新引入的那一类"问题，没有一条是业务理解错误——这本身就说明分阶段是对的。
